## Behaviour kept

- Profiles: standard 16 kHz / 32 kbps / ~14 MB/h, high 22.05 kHz / 64 kbps / ~28 MB/h, mono AAC `.m4a`.
- `stop()` returns the output URI; when idle it returns the partial file of a failed recording once, else null.
- A write failure stops capture, deactivates the session and reports `recordingFailed` once.
- Interruption began: pause, `phoneCall` gap. Ended with shouldResume: resume (errors swallowed). App active while
  paused by an interruption: resume. Old route unavailable: `headphoneDisconnect` gap, capture continues.
- `pause()` keeps `isRecording()` true. Level starts at -160 dBFS and is not reset on stop.
- `-OpenEFBNoAudio` becomes `createAudioRecorder({ audioDisabled: true })`: start throws `audioSessionFailed(noAudioInput)`.
- Gap transcript text `[INTERRUPTION: phoneCall]` / `[INTERRUPTION: other("x")]` via `interruptionGapText` (the
  Swift enum interpolation; `other` uses JSON escaping, which matches Swift for ASCII details).

## Differences (expo-audio cannot do what AVAudioEngine did)

- No PCM buffer callback (`onBufferAvailable`) on the port. Transcription (A3, expo-speech-recognition) captures its own
  audio; whether both can hold the microphone at once is an I3 check. If not, A3 should feed from the recorder instead.
- Output path: expo-audio writes `<Documents>/ExpoAudio/flight-<UUID>.m4a` (Android `<files>/Audio/`); the adapter moves
  it to the output URI on stop (overwrite). If the move fails, `stop()` returns the staging URI. After a crash the file
  is still in staging: L4 crash recovery (FlightRecoveryService) must check `stagingFileName()` there as well.
- No interruption or route-change events reach JS. iOS expo-audio pauses recorders on interruption and resumes them when
  it ends with shouldResume; the adapter polls `getStatus()` every 250 ms and maps an unrequested stop to "began" and
  the return to "ended". The adapter does not call `pause()` on a system-paused recorder, so expo's resume still fires.
  Headphone-disconnect gaps are not detected (dropped; `handleRouteChange` stays in the session for a future native hook).
- The meter is iOS `averagePower` / Android peak `maxAmplitude` in dBFS, not the Swift per-buffer RMS; clamped to [-160, 0].
- Session: expo sets playAndRecord + mixWithOthers + defaultToSpeaker + allowBluetoothHFP. Swift also had
  allowBluetoothA2DP, mode voiceChat, preferred IO buffer 50 ms and preferred sample rate. Stop resets the audio mode
  (`allowsRecording: false`) instead of `setActive(false, notifyOthersOnDeactivation)`.
- Start checks microphone permission (requests it when it can) and throws `microphonePermissionDenied`; Swift relied on
  the system prompt. Callers continue without audio either way.
- Started recorders are created with `new AudioModule.AudioRecorder({})` and configured in `prepareToRecordAsync`
  (no hook; the recorder outlives screens).

## Device-only checks for I3

1. iOS and Android: a 30-minute screen-off recording keeps writing (audio background mode / microphone foreground
   service); the polling timer keeps running in background; file size near 14 MB/h standard, 28 MB/h high.
2. Phone call (or Siri) mid-flight: one `[INTERRUPTION: phoneCall]` transcript row; recording resumes after the call,
   both with the app in background (expo shouldResume path) and when the app is foregrounded (fallback).
3. Android audio-focus loss (call, other recorder): confirm what expo-audio does and that the poll sees it.
4. Bluetooth headset (HFP) input works; note any A2DP routing regressions vs the Swift app.
5. Recorder plus expo-speech-recognition at the same time (A3): both get audio.
6. The staged file moves to `Application Support/efb-212/recordings/<UUID>.m4a` and plays in replay; kill the app
   mid-flight and confirm recovery finds the staged file (partial AAC may lack its moov atom, as with Swift).
7. Simulator / no-mic device: start fails with `audioSessionFailed` and the flight records without audio.
8. Media-services reset (Settings > Developer > Reset Media Services): recording stops with `recordingFailed` and the
   partial file is returned by stop.

## Review decisions kept as Swift parity or deferred (CodeRabbit, PR 27)

- Android MediaRecorder.stop() failures reported only through a later status event are not surfaced after stop; Swift had
  no equivalent. Device check in I3.
- A manual pause() while the system has already paused capture: Swift pauseRecording() only stopped the engine and
  isPausedByInterruption resumed it the same way, so the intent is not tracked (parity).
