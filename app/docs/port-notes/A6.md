## Why a local module and not a library

`react-native-apple-llm` 1.0.16 (the plan's candidate, last published 2026-01-17) streams plain text chunks and builds its
structured-output schema at run time from a JSON description (`DynamicGenerationSchema`); structured output is not streamed. The
Swift engine uses guided generation of one fixed `@Generable` type, with `@Guide` texts and a 1 to 5 range, and streams snapshots
of it for progressive rendering. A library would change what the model is told, lose the streamed structure, and add a
dependency. The local module is the same calls the Swift engine makes (`SystemLanguageModel.default.availability`,
`LanguageModelSession(instructions:)`, `streamResponse(to:generating:)`, `FlightDebrief(finalContent)`) plus
`GeneratedContent.jsonString`, and leaves `package.json` and the lockfile untouched. `@react-native-ai/apple` (an AI SDK
provider) was not considered further: it brings the Vercel AI SDK for one call site.

## Swift behaviour kept

- The system prompt, the reason-to-message mapping (it matches case names or phrases, in this order: not eligible, not enabled,
  not ready; anything else is "Debrief is unavailable right now.") and the strings, including U+203A in "Settings > Apple
  Intelligence & Siri".
- `prewarm()` only creates the session; it does not call `LanguageModelSession.prewarm`, so the model still loads at the first
  response. Nothing is opened until availability is known to be available.
- `generateDebrief` creates the session itself when prewarm was not called, clears the previous result and error first, streams
  partials, then saves a `DebriefRecord` (token estimates null) and sends "Debrief.generated" only after the save succeeded.
- A failed save leaves the completed debrief on screen and sets the error. A failed generation keeps whatever had streamed.
- `discard()` clears the debrief state but not availability.
- A debrief that finishes after the screen was left is still saved (Swift saved whatever finished). Here that is only a narrow
  race, because `discard()` cancels the generation.
- `DebriefError.generationFailed` exists in Swift and is never thrown; it is kept for the type's sake, with its message.

## Differences from Swift

- The model is a port. `availability()` is synchronous (an Expo `Function`), `openSession()` is cheap and synchronous, and
  `generate()` returns a promise; `@Observable` becomes `subscribe()`; database calls are async; ids and times are injectable
  and times are epoch ms; the database is passed per call as the `DebriefStore` slice (`insertDebrief`, `debrief`), as Swift
  passed `recordingDB`.
- **Not offered on Android** (Q8): `DebriefModel.offered` is false there, the model reports unavailable with the reason
  `notOfferedOnThisPlatform` and cannot open a session, and `DebriefEngine.offered` lets a screen hide the feature rather than
  show an "unavailable" message. `src/adapters/debriefModel.ts` decides by `Platform.OS`.
- **The bridge is JSON text.** Every snapshot goes out as the JSON of its `GeneratedContent`; partials are read leniently
  (unknown or mistyped fields are skipped, an unreadable snapshot is skipped) and the final debrief strictly: every field, the
  right types, and a whole-number rating from 1 to 5. Swift's `.range(1...5)` guide limits what the model may write but nothing
  checked it on decode. The module also decodes the final content as `FlightDebrief` natively, as Swift did, so a mismatch
  fails there first.
- `discard()` cancels the generation (Swift let it run to the end), which is why it also resets `isGenerating`. The native
  cancel rejects the pending call with `ERR_DEBRIEF_CANCELLED`; the engine ignores it because the screen it belonged to is gone.
- `error` is an `Error`; `debriefErrorMessage(error)` gives the text Swift showed for `error.localizedDescription` (an
  `AppFailure` the way `errorDescription` words it, any other error by its message). A session that cannot open is
  `AppFailure(debriefFailed, DebriefError(sessionUnavailable))`, as in Swift.

## JS-only guards (no Swift equivalent)

- Work that outlives a `discard()`, a newer generation or a newer load is dropped by an epoch check: a late partial, result,
  error or loaded record can never overwrite what is on screen, and a finished stale generation does not end the new one.
- A `generateDebrief` call while one is generating is ignored (a `LanguageModelSession` serves one request at a time).
- A model whose `availability()` throws reads as unavailable; a `prewarm` that cannot open a session leaves it to
  `generateDebrief`, which retries and reports; a throwing `close()`, telemetry hook or listener cannot break the engine.
- The native module cancels a stale generation when a new one starts and tags every event with a request id, so snapshots of an
  earlier request are never delivered to a later one. Its session and generation are guarded by a lock, because `openSession`
  and `closeSession` run on the JavaScript thread and `generate` on the module's background queue.
- A saved debrief that finishes loading while a generation is running is dropped, so it cannot cover the streaming one.

## Device-only checks for I3

1. iOS 26 device with Apple Intelligence on: availability is available; generating shows the summary, observations and
   improvements appearing progressively, and the finished debrief is saved and reloads (the lifecycle is
   check, prewarm, generate, discard).
2. The three unavailable states (device not eligible, Apple Intelligence off, model still downloading) show the three messages.
3. Leave the screen mid-generation: no crash, no events afterwards, memory returns to its baseline (the model holds about 1.2 GB),
   and the next debrief works. Regenerate (discard then generate) gives a fresh session.
4. Airplane mode: a debrief still generates (nothing leaves the device).
5. Android: the debrief is not shown anywhere.
6. iOS earlier than 26 (only if the deployment target stays below 26): `FoundationModels` must not stop the app launching. Q11 sets
   iOS 26 as the minimum and `app.config.ts` still says 16.4; raise it, or check on an older simulator that the framework is
   weak-linked. The module guards every call with `#available(iOS 26.0, *)` and reports `osNotSupported`.
7. The iOS CI job is the first real compile of the Swift module, including `@available(iOS 26.0, *)` on the `@Generable`
   types; on this ticket it was only parsed and type-checked against stubs.
