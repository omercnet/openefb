# D4 port notes: recording database

Code: `src/data/recording/` (`migrations.ts`, `records.ts`, `recordingDb.ts`). Tests: `tests/data/recording/recordingDb.test.ts`.
No importer step: the RN app starts with a clean slate (plan section 10), so nothing reads the Swift `recording.sqlite`.

## Design

- Same tables, column names, indexes and migration identifiers as GRDB (`v1`, `v2_debrief`,
  `v3_nullable_transcript_confidence`, `v4_flight_route_legs`, `v5_debrief_generatedAt_epoch`), tracked in `grdb_migrations`.
  The whole chain is kept, not collapsed into one schema, so the chain-migration characterisation tests port unchanged;
  v5 is a no-op on a fresh database.
- `openRecordingDatabase(db)` = `PRAGMA journal_mode = WAL` + `migrateRecording`, mirroring `RecordingDatabase.init`. Each
  migration runs in one transaction with its bookkeeping row. The file lives in its own `recording.sqlite` (separate from
  `kanaf.sqlite`); the adapter that opens it on device is `openExpoSqliteDb('recording.sqlite')`.
- Time columns stay REAL Unix seconds (the numeric shape GRDB reads and v5 expects); the API is epoch ms and converts with
  `Math.round(s * 1000)`, so millisecond values round-trip exactly.
- Ids are lower-case UUID text. (GRDB binds `UUID` as a 16-byte blob in TEXT columns; irrelevant without an import.)
- Methods match `RecordingDatabase` one to one. Additions: `insertTrackPoints` (batch in one transaction, for the recorder's
  buffered fixes). `saveRouteLegs`, `insertDebrief` and `deleteFlightData` are transactions like GRDB's `write`.
- "Recovery queries": `flightIDsWithRecordedData()` is the only query FlightRecoveryService needs (track points UNION
  transcript segments); phase-marker-only flights are not recovered, as in Swift.

## Swift behaviour preserved

- `debrief_results` is replaced per flight (delete then insert); a flight with no track and no transcript is not listed.
- v3 turns the `-1` confidence sentinel into NULL and keeps a real `0.0`.

## Ported tests

- RecordingDatabaseChainMigrationCharacterizationTests: 5 of 5.
- RecordingDatabaseMigrationTests: 3 of 3.
- DebriefSchemaTests: 3 of 6 (`debriefRecordRoundTrip`, `debriefRecordOverwrite`, `debriefRecordDelete`).
- New: WAL on a file database, ordering, batch insert and its rollback, millisecond precision, phase marker end update,
  route legs, recovery scan, `deleteFlightData` isolation, migration rollback.

## Not ported here (with reason)

- DebriefSchemaTests `flightDebriefCompiles`, `phaseObservationCompiles`, `debriefRecordFromFlightDebrief`: they exercise
  `FlightDebrief`/`PhaseObservation` and `DebriefRecord.fromFlightDebrief`, which are L5 (debrief).
- AutoStartTests (6): AutoStartGate logic, L4; it only shares the port-map row.
- ReplayEngineTests, FlightRecoveryTests, FlightPersistenceTests, FlightPersistenceStopPathCharacterizationTests: the
  services they test (L8, L4) are not ported yet; they use this database through `RecordingDatabase` and port with those
  tickets (`makeRecordingDatabase(db)` over `openNodeSqliteDb()` is the test double).
- Swift tests use a temp-file `DatabasePool`; Jest uses an in-memory `Db` except where the file matters (WAL, reopen).

## Swift differences

Dates are epoch ms in the API (Swift `Date`); ids are text. No behavioural difference found.
