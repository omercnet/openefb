# A7 notes: recording file, replay audio and airport adapters (carry-forward)

Wave 1 left the platform half of three interfaces unbuilt: `RecoveryAudioFiles` (L4, `flightRecovery.ts`) plus the
`removeFile` and Application Support root of `FlightPersistenceService`, `ReplayAudioPlayer` (L8, `replay/types.ts`) and
`AirportLookup` (L4, `flightPersistence.ts`). Swift did this inline: `FlightRecoveryService.audioDuration` and its
`FileManager` calls, `FlightPersistenceService` file removal, `ReplayViewModel.loadFlight` (resolve the stored path,
`fileExists`) and `ReplayEngine.loadFlight` (`AVAudioPlayer`). There are no Swift test cases for any of it, so every test
below is new.

## Files

- `src/adapters/recordingFiles.ts`: `createRecordingFiles()` implements `RecoveryAudioFiles` (`listFileNames`,
  `pathFor`, `exists`, `durationSeconds`, `creationDate`) and adds `removeFile` and `appSupportRoot`. Pass `files` as
  `audio` to `FlightRecoveryService`, `files.removeFile` and `files.appSupportRoot` to `FlightPersistenceService`, and
  build the recorder's output URI with `audioFileUri(files.appSupportRoot, id)` so the three agree.
- `src/adapters/m4aDuration.ts`: reads a duration from an MPEG-4 file's `moov/mvhd` box (pure, over a `ByteReader`).
- `src/adapters/replayAudioPlayer.ts`: `createReplayAudioPlayer(storedPath)` returns the `ReplayAudioPlayer` for
  `ReplayEngine.loadFlight`, or null when there is no stored path or no file.
- `src/adapters/airportLookup.ts`: `createAirportLookup(aviationDatabase)` implements `AirportLookup`.
- `tests/support/fakeExpoFileSystem.ts`, `tests/support/m4aBuilder.ts`: an in-memory expo-file-system and an MP4 byte
  builder for the tests. L4 and L8 already have in-memory `RecoveryAudioFiles` and `ReplayAudioPlayer` fakes in their tests.

## Differences from Swift

- Audio duration: Swift read `AVAudioFile.length / sampleRate`, which decodes the file's own metadata and fails on a file
  it cannot open. expo has no file-metadata API short of creating a native player, so the adapter reads the MP4 movie
  header. Both give 0 for the file a crash leaves behind: a recorder writes `moov` when it stops, so an unfinished file has
  none (A2 notes say the same of Swift). It also gives 0 for a header that is cut off, has timescale 0 or marks the
  duration unknown, and never reads media data, so an hour of audio costs a few small reads.
- Creation date: `File.creationTime` (epoch ms), `null` when the platform has none or it is not a number.
- Application Support: expo-file-system has no constant for it. On iOS it is `<Documents>/../Library/Application Support`,
  the sibling of Documents. On Android it is `Paths.document` (the private files directory), the nearest equivalent.
- `listFileNames` lists files only (sub-directories are skipped) and is empty when the recordings directory does not exist
  yet. It rejects when the directory cannot be read; the recovery service turns that into "no files", as Swift `try?` did.
- Replay audio: `AVAudioPlayer` becomes an expo-audio player. Seeking is asynchronous there (a rejected seek is dropped),
  the maximum rate is 2.0 as in Swift (the engine already mutes above it), and a player that fails to create no longer fails
  the whole load: Swift threw out of `loadFlight`, here the flight replays without sound. Every native call is guarded,
  because the engine calls the player from a timer where a throw would go uncaught, and after `stop()` the player is
  released and every call does nothing.
- `AirportLookup` drops runways and frequencies (`nearestAirports` returns them, the persistence service needs icao, name and
  type) and rejects when the database does; `FlightPersistenceService` reads that as "no airports", as Swift `try?` did.

## Device-only checks for I3

1. iOS: `applicationSupportDirectory()` is the directory `FileManager` reports for Application Support (the recorder
   writes there, replay reads there, and the stored relative path round trips).
2. Kill the app mid-recording on both platforms: recovery finds the audio (A2 notes list where the staged file is), reports
   duration 0 for the unfinished file and the file's creation date as the start.
3. A finished one-hour recording reports about 3600 s on both platforms.
4. Replay: audio starts at the position the map shows, 1x and 2x stay in step, 4x and 8x are silent, and leaving the
   screen releases the player (the screen must call `ReplayEngine.cleanup()`).
