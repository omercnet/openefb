# A5 notes: first-party usage counters (replace TelemetryDeck and MetricKit)

Sources: `Services/TelemetryService.swift` (148 lines), `efb-212Tests/ServiceTests/TelemetryTests.swift` (4 cases) and the nine
`Telemetry.signal` call sites. Owner decision Q7: first-party counters on our own Cloudflare Worker, no identifiers, and the privacy
policy updated to say so (as a draft for cutover, below). Plan section 3.7: free services only, crash reports come from the stores. Plan section 6.3 item 4: the counter
carries the active update id, so launches per OTA update can be compared.

**Nothing here is deployed or switched on.** The Worker (`web/telemetry`) is code and tests only; the app sends nothing until the
owner deploys it and builds with `EXPO_PUBLIC_TELEMETRY_URL` set (steps in `web/telemetry/README.md`).

**`PRIVACY.md` is not changed.** It is the public policy for the Swift app that is live in the App Store today, which still uses
TelemetryDeck and SFSpeechRecognizer, so new wording merged now would make it wrong about the shipping app. The new wording is a
draft, `app/docs/privacy-rn-draft.md`, that replaces `PRIVACY.md` at cutover (a release step the owner approves). Its header lists
the two claims the owner must confirm then: the host name `openefb-telemetry.omerc.workers.dev` and "Cloudflare keeps them for three
months" (retention must match the deployed Worker config). An earlier commit of this branch changed `PRIVACY.md` directly; a later
revert commit undoes it, so the branch leaves the file as it is on `main`.

## Files

- `web/telemetry/` (Cloudflare Worker, Analytics Engine): `src/schema.json` is the vocabulary and the source of truth; `src/schema.ts`
  compiles it into a strict row checker; `src/handler.ts` is `POST /v1/counters`; `wrangler.toml` has the `COUNTERS` binding, not
  deployed. Own `package.json` and lockfile, as the other `web/*` packages. `test/appClient.test.ts` runs the app's real client
  (facade and transport, imported from `app/src`) against the real handler; `vitest.config.ts` lets it do that in CI, where `app/` has
  no `node_modules`.

  `schema.json`), `validateSignal`, `validateRow`, `durationBucket`. The event and parameter types come from the table, so a call that
  passes a free-text value or an unknown event does not compile.
- `src/domain/telemetry/counterBuffer.ts`: counts per distinct (event, parameters, app version, platform, update, region), capped at
  200 rows, and the stored form of the backlog (`serializeRows`, `parseRows`, checked row by row).
- `src/domain/telemetry/telemetry.ts`: `Telemetry`: `signal`, `flush`, `setEnabled`, `start`.
- `src/domain/telemetry/dimensions.ts`: `appVersionDimension`, `updateDimension` (pure).
- `src/domain/ports/telemetry.ts`: `TelemetryTransport`, `TelemetryStorage`, `SendOutcome`, and their fakes.
- `src/adapters/telemetryTransport.ts` (HTTP; `telemetryEndpoint` parses the setting), `telemetryStorage.ts` (over
  `expo-sqlite/kv-store`, no new dependency), `telemetry.ts` (`createTelemetry`, `startTelemetry`: launch count, flush when the app
  goes to the background and when it comes back).
- `src/domain/recording/recordingCoordinator.ts`: an optional `telemetry` dependency and the two `Recording.*` signals that L4 left out
  as plumbing (`docs/port-notes/L4.md`). `src/domain/debriefEngine.ts` (A6): its `telemetry` type now names the one event it sends.
- `app/docs/privacy-rn-draft.md`: the policy text for the rewritten app, a draft until cutover, with a header for the owner;

## Swift behaviour kept

- The Settings toggle "Share anonymous usage data", Swift key `telemetryEnabled`, **on until the pilot turns it off**; off stops
  everything at once. In the app: `Telemetry.setEnabled`, key `telemetryEnabled` in the key-value store.
- Nothing carries coordinates, airport identifiers, tail numbers, names or free text: every parameter is a closed list, or a short
  lower-case pack name for `ChartPack.installed`.
- The event names and their parameters, unchanged: `Navigation.screen` (`screen`: map or log), `Recording.started`,
  `Recording.stopped` (`durationMinutes`: 0-15, 15-60, 60+), `FlightPlan.activated`, `Debrief.generated`,
  `ChartPack.installed` (`product`, `edition`), `Israel.briefingOpened`, `Israel.fplShared` (`method`: share or email).
- The region travels with every count (Swift: the `appRegion` default parameter), read when the signal happens.
- Off until configured: Swift did nothing without `TELEMETRYDECK_APP_ID`; the app does nothing without `EXPO_PUBLIC_TELEMETRY_URL`.

## Differences from Swift

1. **Counters, not signals.** TelemetryDeck received one signal per event with a session and a hashed vendor id. The app adds
   counts up on the device (per event, parameters and four labels) and sends batches of at most 40 rows. There is no time stamp,
   session, user, device or installation id, and nothing says the order of events. Swift `TelemetryDeck.Session.started` is gone.
2. **Labels.** App version (x.y.z), platform, OTA update id (or "embedded") and region. Swift's iOS version and device model are not
   sent: they add fingerprinting surface (Q7: no identifiers) and the plan needs only the update id.
3. **No MetricKit crash and hang summaries** (3 dropped tests above). Crash numbers come from App Store Connect and Play vitals.
4. **Own backend.** `POST /v1/counters` on a Worker, stored in Workers Analytics Engine (free plan, data kept three months). The
   Worker reads no request header and no `request.cf`; tests enforce it. The app posts a JSON body and a content type, nothing else,
   without credentials.
5. **Release builds send over HTTPS only; development builds only to a Worker on the same machine** (`localhost`, `127.0.0.1`,
   `[::1]`, `10.0.2.2`), so counts from someone running the app from source never reach the deployed Worker.
6. **No import of the Swift choice.** The owner decided the app starts with a clean slate (no import of Swift user data), so a pilot
   who turned the Swift toggle off starts with it on again. The draft policy tells the pilot where to turn it off.
7. **Not in Swift:** `start()` reads the stored choice and the unsent backlog; counts survive the app being killed; the backlog and the
   choice live on the device only.
8. API shape: Swift's `start(region:)`, `setEnabled(_:region:)` and `setRegion` become `start()`, `setEnabled(enabled)` and a
   `region` callback given to `createTelemetry`.

## Swift quirks kept

- `durationBucket(NaN)` is "60+" (no `switch` case matches, so it reaches `default`) and a negative length is "0-15".

## JS-only guards (no Swift equivalent)

- Every signal is checked against the schema when it is counted and again when the stored backlog is read; a bad one is dropped by
  itself. The Worker checks every row again and drops what does not fit, so an older Worker simply ignores a newer event.
- A choice that cannot be read means off for that session (not on): a failed read must not count a pilot who opted out. A backlog
  that an earlier opt-out could not delete is never sent.
- A flush that is running is joined, never doubled. A send that comes back after the choice changed (off, or off and on again) is
  stale and puts nothing back. Storage is used one operation at a time in the order things happened, and nothing is written before
  the stored backlog was read, so an old write cannot land after a new one or after an opt-out's removal.
- A send is at most once: counts handed to the transport leave the stored backlog, and come back only when the answer is "try again"
  (no network, timeout, 408, 425, 429, 5xx, or an answer that is not the Worker's, such as a captive portal page). A 4xx is a refusal
  for good and drops the batch.
- `signal` never throws and never waits; `flush` never rejects.

## Device-only checks for I3

- A real request from a device build to a deployed Worker (nothing has been sent anywhere yet).
- `Updates.updateId` and `Updates.isEmbeddedLaunch` on an embedded build and on a downloaded update (the tests mock them).
- That `expo-sqlite/kv-store` keeps the backlog across a kill of the app (the tests use an in-memory store).
