## Swift differences

- Time is epoch ms; `Date()` and `Task.sleep` go through an injected `Clock` (tests use `FakeClock`).
- Collaborators (audio, transcription, track recorder, recording store, audio file path) are injected as the
  interfaces in `collaborators.ts`; the Swift `as? AudioRecorder` / `as? TranscriptionService` downcasts for the
  interruption-gap, error and phase-provider wiring became optional methods on the interfaces.
- `TrackPoint`/`PhaseMarker` are local plain types in `types.ts` until the data ticket (D) lands record types.
- `State` (@MainActor @Observable) is `RecordingState`, a plain object with `subscribe()`.
- `ScenarioTrackRecorder` in the scenario test stands in for the A1 TrackRecorder (one point per fix).

## Swift behaviour preserved (not bugs, but easy to mistake for them)

- `stopRecording` during a countdown returns null and leaves the countdown running (pinned by a Swift characterization test).
- Audio or transcription start failure is swallowed; recording continues.
- The detector tracks `maxCruiseAltitude` but never uses it.
- A recording whose first fixes are above rotation speed goes preflight -> departure with no taxi phase.

## Review findings declined (Swift parity), PR #35

- `stopRecording` has no re-entry guard on `stopping`; a second call during the awaits repeats the stop. Same in Swift.
- The auto-start monitor does not cancel a running countdown when speed drops (it "lets the countdown proceed"), and
  `startCountdown` does not abort if a manual start changes the status mid-count. Same in Swift.
- JS-only start guards (no Swift equivalent, its tracker calls do not throw): a failed startup best-effort stops the tracker,
  and rolls back only its own start session (a stop or newer start is not cleared).

## L4 part 2: persistence and recovery

| Swift                                             | TS                                        |
| ------------------------------------------------- | ----------------------------------------- |
| Services/Recording/FlightPersistenceService.swift | src/domain/recording/flightPersistence.ts |
| Services/Recording/FlightRecoveryService.swift    | src/domain/recording/flightRecovery.ts    |

Tests (Swift names kept, over the real D2/D4 data layer on node sqlite): FlightPersistenceTests 3/3,
FlightPersistenceStopPathCharacterizationTests 8/8 (the `ctx.hasChanges == false` assertions have no equivalent; the
"saves explicitly" case asserts both rows are in the stores instead), FlightRecoveryTests 5/5, plus 2 added tests (`saveFailed` on a duplicate flight, and
rollback when the logbook insert fails).

Differences:

- SwiftData ModelContext becomes the main `Db`: the flight and draft logbook rows are inserted in one `db.transaction`
  (repositories built on the tx), so a failure rolls back both, like Swift's single `save()`. `saveFailed` means the
  transaction was rejected. Added a test where the logbook insert fails and no flight row remains.
- File access (delete, list, exists, audio duration, creation date) and the Application Support root are injected
  (`removeFile`, `RecoveryAudioFiles`, `appSupportRoot`); the AVAudioFile duration and FileManager calls belong to the adapter.
- The airport lookup is an injected async interface; a lookup error reads as "no airports" (Swift `try?`).
- `LogbookViewModel.createFromRecording` (ticket U7) is inlined with a TODO(U7).
- Flight ids are compared lower-case (the data layer stores lower-case UUID text; Swift compared UUID values).
- `PhaseMarker.phase` in `types.ts` is now `string`, matching the data layer.
