### Swift differences

Intentional or unavoidable, one line each:

- Settings errors are surfaced where Swift's `try?` / `AppStorage` could not fail: `regionSaveError` keeps the Swift text; a
  display-mode or privacy write that fails shows "Changed, but it could not be saved: ..."; an unreadable setting at load shows
  "Some settings could not be read: ...". Reads that Swift does with `try?` still degrade to the default (data cycle unknown, no
  active pilot, default region).
- JS-only guards: `saveNotamCredentials` puts the previous id back when the secret write fails (an old secret next to a new id
  authenticates as nobody); `removeNotamCredentials` tries both removals and rethrows the first error; after a failed removal
  the status is re-read so it does not keep saying "Configured".
- An unreadable telemetry flag reads as off (Swift cannot fail here; a privacy choice must not come back on because storage failed).
  `setTelemetryEnabled` is called at once, before the flag is saved, so an opt-out does not wait on storage.
- Region, display-mode and privacy changes apply at once and are saved through one serial queue with load and the NOTAM actions, so
  a slow earlier write cannot land after a later one. A throwing app notification (`onRegionChange`, ...) is reported next to the
  setting instead of aborting the change.
- `formatFileSize` is a stand-in for `OfflineSizeFormatter` (decimal units, adaptive digits, no zero padding); M3 owns the real
  one and Settings takes it as a dependency.
- `progressPercent` clamps to 0...100 and reads NaN as 0 (`Int(NaN)` traps in Swift). `formatCycleDate` and `aviationDataRow`
  read a non-time value as "unknown" / "Cycle unknown".
- The TestFlight sentence under Feedback is shown on iOS only. The NOTAM footer still says "iPad Keychain" (verbatim); wording for
  Android belongs to the string-table pass (U6).
- Picker rows expand inline with radio rows (a menu `Picker` has no React Native core equivalent); `Link` rows do nothing when the
  URL cannot be opened, as SwiftUI does.
- "N to renew" uses the L6 rules, so it carries L6's owner decisions (UTC day arithmetic; landings dated after now do not count).
- `Disclaimers` and onboarding copy keep the word "iPad" (verbatim).

### Owner-approved deviation from Swift (Q5, 2026-11-12)

- **A pilot profile created while none is active becomes the active one** (`createPilotProfile`, in one transaction). Swift's
  `PilotProfile.init()` has `isActive = false` and `addProfile()` never activated it, so a first-time user with one profile saw only
  "Add Pilot Profile" (Pilot Info, Currency Status and Night Landings show for the active pilot only, the list needs two). A second
  profile leaves the active one alone; deleting the active one leaves none active, as in Swift. `pilotScreenLayout` is unchanged
  (the state can still come from data); its test now says so. Tests: first profile active, second not, an existing active one is
  respected, delete.

### Swift bugs and quirks preserved (owner approval needed to change)

- Deleting an aircraft does not clear its route network preference (the Swift UserDefaults key stays).
- A new aircraft is not made active; tapping a row is the only way (aircraft rows always show, so this is not a dead end).

### Swift differences

- Swipe actions (Edit, Delete) have no React Native core equivalent: each aircraft row has a visible Edit button and each editor
  ends with Delete, which asks first (Swift deleted on a swipe without asking).
- Failed writes are shown where Swift swallowed them (`catch { // changes still pending }`): every store has an `error` and a
  `saving` flag; a second tap while a write runs is refused so a double tap cannot create or log twice. Reads that fail keep the
  list on screen and say so (Swift showed an empty list, which reads as "no aircraft").
- Confirming a logbook entry is one transaction (entry confirmed, edits saved, landings appended to the active pilot); Swift
  confirmed even when the pilot fetch failed (`try?`). Confirming an already confirmed entry does nothing, so landings are never
  counted twice, and the data layer refuses to edit a confirmed entry (Swift locks it in the view only).
- Night landings that would not read back (a NaN date is stored as null, a count outside the stepper's 1 to 10) are refused
  before storage: one malformed entry makes `decodeNightLandings` return an empty list, and the next write would erase the history.
  The active pilot is resolved inside the queued job, so a queued select decides who gets the landings; an unloaded store loads
  first instead of dropping them.
- A new aircraft writes its route network first and clears it again if the insert fails, so a failed save leaves nothing behind and
  a retry cannot duplicate the aircraft.
- Block time: Swift edits a full-precision `Double` shown to one decimal, so an untouched field keeps the stored seconds exactly
  (3727 s stays 3727 s); this port keeps the same rule. Text that is not a number is an error the form shows (Swift quietly kept the
  old value), and a negative block time is refused.
- Number text follows Swift: stored numbers are shown as `String(Double)` ("180.0"), read with `Double(text)` and `Int(text)`
  (no whitespace, "." only, "12,5" reads as none), and `%.1f` rounds an exact tie to the even digit (900 s is 0.2 h), which `toFixed`
  does not. JS-only guards: non-finite values read as none or 0.
- Lists show newest first like the Swift view models (the D2 repositories list oldest first, so the stores sort).
- The route network picker shows for every region (Swift: the same). Dates use the device's local calendar and locale; L6's currency
  arithmetic is UTC (L6.md), so a day boundary can differ by up to a day near midnight.
- `AI Debrief Available` in the confirmed entry's summary is data-driven (`hasDebrief`); it never appears on Android in v1 because
  the AI debrief is hidden there (owner decision Q8), so nothing is gated here.

### Capture layout (U7 layout fix)

The screens used to be mounted in a 400 pt column (`StripFrame`) and showed in a third of an iPad. The Swift capture host
(`CaptureRouteHost.swift`) puts each in a full-screen `NavigationStack`, so the capture frame (`ScreenFrame`) is now full width.
Settings, Disclaimers, Aircraft & Pilot, Pilot Profile and the logbook entry (Edit Entry, Flight Details) sit at SwiftUI's default
large title mode, so `FormScreen` takes `largeTitle` (34 pt bold under the bar, scrolling with the list); Edit Aircraft, Edit
Pilot and Log Night Landings stay inline, as in Swift. Not matched: iOS 26 draws the toolbar buttons as floating glass pills and
the large title collapses into the bar on scroll; the RN bar is flat and the title scrolls away. In the shell (I1) Settings opens
from the Log stack in the strip (`LogStackView.swift`) and the other screens push from it; I1 decides the container there.
