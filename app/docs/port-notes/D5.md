# D5 port notes: aviation database access

Scope of PR 1 (this file is extended by PR 2 for the Israel database): `Data/AviationDatabase.swift` to
`src/data/aviation/` (`aviationDatabase.ts` queries, `install.ts` versioning and copy-on-first-launch,
`types.ts`), platform half in `src/adapters/aviationDb.ts`.

## R-tree on the Node sqlite used in Jest (plan 3.1 UNVERIFIED): VERIFIED

Node v26.8.2 `node:sqlite` creates `rtree` and `fts5` virtual tables and answers the R-tree overlap queries and FTS5
MATCH queries the Swift code uses. Evidence: the synthetic-schema tests (box edges, float32 R-tree rounding at the
inclusive edge, FTS prefix search) and `tests/data/aviation/bundled.test.ts`, which opens the real
`efb-212/Resources/aviation.sqlite` (12 MB, R-tree and FTS5 tables included) read from `tests/support`-style Node
sqlite. All 67 app tests pass.

## Design

- Queries take the `Db` interface (`createAviationDatabase(db)`), async, coordinates as `{ lat, lon }`, times as epoch ms
  (`AviationDataCycle.effectiveMs/expiresMs`). Method names: `airport`, `airportsNear`, `toweredAirportsNear`,
  `nearestAirports`, `searchAirports`, `airspacesNear`, `airspacesContaining`, `navaidsNear`, `dataCycle`.
- Platform piece: `AviationInstallFiles` + `AviationInstallPlatform` are declared in `src/data/aviation/install.ts`.
  `src/adapters/aviationDb.ts` implements them with expo-file-system and expo-sqlite (install directory is expo-sqlite's
  default database directory, as in the spike). Tests use `tests/data/aviation/nodeFiles.ts` (node:fs, file-backed
  node:sqlite).
- The adapter keeps the spike exports (`openAviationDb`, `airportsInBox`, `AIRPORTS_IN_BOX_SQL`, `DB_NAME`) so the map
  and self-test screens are untouched; `openAviationDb` now goes through the install flow. New: `openAviationDatabase()`.
  The `no-require-imports` warning is fixed with a one-line disable on the Metro asset `require` (Metro needs the literal
  `require`; there is no import form for an untyped, git-ignored `.sqlite` asset).
- The SHA-256 of the bundle comes from the platform (`AviationInstallFiles.bundledSha256`): expo-file-system's native
  `File.digest('SHA-256')` on device, node crypto in tests. No JS hashing at launch and no new dependency. Not measured
  on device (a 12 MB native digest should be tens of milliseconds, as in Swift).
- `airspacesContaining` keeps Swift's 30 NM candidate radius. A radius of 0 would decode fewer rows (a containing
  airspace always has a box containing the point) and is a candidate optimisation, left out under the no-improvement rule.

## Swift differences (all deliberate or unavoidable)

1. Model types (`Airport`, `Runway`, `Frequency`, `Navaid`, `Airspace`, enums) are defined in
   `src/data/aviation/types.ts` because the domain track (L1) has not put them on main. Field names and raw values match
   Swift; switching to the domain types later is an import change. Frequency and airspace ids are UUID strings
   (upper case, random when the stored id is not a UUID, as Swift's `UUID()` fallback).
2. `dataCycle()` parses `yyyy-MM-dd` strictly (real calendar date or null). Swift's `DateFormatter` accepts some
   out-of-range days by rolling over. No test covers it; the bundled data is valid.
3. Great-circle distance uses `domain/geo.distanceNm` (asin form) instead of Swift's atan2 form: identical to about 1e-12
   NM, can only matter for an airport exactly on a search-circle boundary.
4. `installBundledDatabase` returns whether it copied (Swift returned the installed URL); paths are the platform's.
   A missing bundle throws `AppFailure({ kind: 'databaseCorrupted' })`; an unrecoverable open throws
   `databaseMigrationFailed`, as `EFBError` did.
5. Swift bugs preserved: `airports/airspaces/navaids(near:)` divide by `cos(lat)` with no guard (only
   `toweredAirports` clamps at 0.01); `airspacesContaining` only considers airspaces whose box is within 30 NM of the point.

# D5 PR 2: Israel aviation database

`Data/IsraelAviationDatabase.swift`, `IsraelAviationDatabaseProtocol.swift` and `IsraelAviationModels.swift` to
`src/data/aviation/israelDatabase.ts` (queries, the protocol as the `IsraelAviationDatabase` interface),
`israelTypes.ts` (models, bounds, airspace geometry helpers) and `israelOpen.ts` (install and schema check); adapter
entry `openIsraelDatabase(assetModule)` in `src/adapters/aviationDb.ts`.

## Design and differences

- Async methods over `Db`; coordinates `{ lat, lon }`; polylines, polygons and runway ends use `Coordinate`. Optional
  Swift arguments become defaults (`network = 'cvfr'`, `altitudeFeetMSL = null`). Overloads are renamed:
  `airspacesContaining`, `airspacesNear`, `airspacesOfKind`, `runwaysOfAerodrome`, `runwaysIn`, `aerodromesIn`.
  `IsraelGeoBounds.init(center:radiusNM:)` is `boundsAround`; `wholeCountry` is `WHOLE_COUNTRY`.
- `knowsPoint` and `segment` (the `IsraelRouteSegmentLookup` the NOTAM closure mapper uses) are async here and keep the
  Swift behaviour of answering "unknown" (false / null) when the lookup fails. The mapper port must await them.
- Swift opened the file in place from the app bundle. expo-sqlite opens only files in its own directory, so the file is
  installed with the same versioned install as aviation.sqlite (copy when missing or when its version, size or SHA-256
  changed). The schema check is the Swift one (`metadata.schema_version == 3`). Errors map as in Swift: missing file is
  `regionDataUnavailable` (region "Israel"), unreadable or wrong schema is `databaseCorrupted`.
- The adapter takes the Metro asset module as an argument and does not `require` it, so builds that do not ship
  israel-aviation.sqlite keep bundling. The first UI consumer adds
  `require('../../assets/israel-aviation.sqlite')`, the `assets/` gitignore entry and the CI copy step (as for
  aviation.sqlite in `.github/workflows/app.yml`); those are shared files and are not touched here.
- Hebrew strings (network names, test text) are copied verbatim from Swift; U6 inventories Hebrew for i18n.
- Swift `Dictionary`/`Decodable` behaviours preserved: unknown enum values in required columns (airspace kind,
  aerodrome type, use, ppr, review status) are `databaseCorrupted`; lenient ones fall back (point kind `onRequest`,
  network `cvfr`, activity `unspecified`); an unparseable `lsa_weekend_rule` or `source_urls` is dropped, not fatal.
- Tests run on the real `efb-212/Resources/israel-aviation.sqlite` (R-tree and LIKE on Hebrew text work on Node sqlite).
