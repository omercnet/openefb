# U8 port notes: recording, replay, debrief and flight detail screens

U8 is the second half of the app-screens track. U8a (the recording controls) is first; U8b (replay, debrief, flight detail)
adds its section below it. The screens sit on the L4 recording coordinator (U8a) and the L8 replay and L5 debrief engines (U8b).
No navigation and no app-startup wiring here; that is the app shell (I1).

## U8a: recording controls

### Ported

- `ViewModels/RecordingViewModel.swift` -> `src/ui/state/recordingStore.ts`, a vanilla Zustand store over `RecordingCoordinator`:
  `startRecording`, `press` (what a tap on the record button does), `requestStop` / `cancelStop` / `confirmStop`
  (stop, store the plan legs, persist through `FlightPersistenceService`, map `savedTrackUnreadable` and `saveFailed` to the
  `recordingFailed` errors), `cancelCountdown`, `dismissError`, `dismissDiscardedNotice`, the microphone flag.
  The pure rules are in `src/domain/recording/recordingNotices.ts`: `problemSeverity`, `shouldShowDiscardedNotice`, `pressAction`,
  the notice copy (verbatim from Swift) and `problemDetail` (the cause without the "Recording failed:" prefix).
- `Views/Map/RecordingOverlayView.swift`: `RecordingNotices` -> `src/ui/recording/RecordingNotices.tsx` (microphone off, a
  recording problem with its severity, recording not saved; the 4 pt leading rule in the notice colour; 60 pt buttons) and the
  "End recording?" confirmation -> `StopRecordingDialog.tsx`. The glyphs the notices need are in `ui/recording/icons.tsx`.
- `RecordButton`, `AudioLevelMeter`, `formattedElapsedTime` and the lit segments are U3's (`ui/flightLog/RecordButton.tsx`, #47).
  This ticket does not duplicate them: the record button binds to `store.getState().press()` and reads `status`,
  `elapsedTime`, `audioLevel` and `countdownRemaining` from the store.
- New seam `MicrophonePermission` (`domain/ports/microphonePermission.ts`, fake included) with an expo-audio adapter
  (`adapters/microphonePermission.ts`): Swift read `AVAudioApplication.shared.recordPermission` directly, which has no JS
  equivalent. `openSettings` is `Linking.openSettings()` (Swift: `UIApplication.openSettingsURLString`).

### Seams the app shell (I1) fills

- Create the store with `createRecordingStore(deps)`. `deps.coordinator` is the `RecordingCoordinator`, `deps.microphone` is
  `createMicrophonePermission()`, `deps.persistence` is the `FlightPersistenceService`. `deps.activeProfileIds` and
  `deps.activeRouteLegs` read what Swift read from `AppState` (`activeAircraftProfileID`, `activePilotProfileID`,
  `activeRoute.legs`). `deps.saveRouteLegs` is `RecordingDatabase.saveRouteLegs`.
- Mount `<RecordingNotices store />` in the strip under the record button and `<StopRecordingDialog store />` once.
- The record button calls `press()`. It returns `'problem'` when a start went ahead with the microphone off or failed: that is
  where the shell gives the warning haptic.
- Other screens that read `AppState.recordingStatus`, `currentFlightPhase`, `recordingElapsedTime`, `audioLevel` or
  `activeFlightRecordID` (the log strip, Flight Detail disabling Replay) read the store instead of a copy.
- Nothing else drives the store: it follows the coordinator, so an auto-started recording needs no call.

### Not ported

- `recentTranscripts` (last five live transcripts). The L4 `RecordingState` has no such field, and no Swift view reads
  `AppState.recentTranscripts` (the shell appends to it; nothing displays it).
- Haptics on the record button (shell), the `AppState` mirror writes (see the seam above), the 0.5 s sync loop (see below).

### Swift quirks kept (owner approval needed to change)

- The plan's legs are stored with the flight only when the plan has legs (`saveActiveRouteLegs` guards `!legs.isEmpty`). A plan cleared
  during a recording leaves the legs stored at the start, and the CVFR debrief then compares against them. Fix, if wanted: call
  `saveRouteLegs([], flightId)` at stop when the list is empty.

### Swift differences

- **No polling.** Swift copied the coordinator's state every 0.5 s. The store subscribes to the coordinator, so a countdown tick,
  a failure or the end of a recording shows at once. The coordinator's `lastError` is still surfaced once and cleared.
- **Stop confirmation.** Swift's `confirmationDialog` is a popover anchored on the button (iPad) or an action sheet (iPhone).
  The port is a centred modal with the same title, message and two choices, on both platforms.
- **Microphone permission is asked through the port, on a start only.** `undetermined` is asked once (the system prompt) as in
  Swift. A `denied` answer starts the recording anyway, with the notice (the GPS track still records), as in Swift.
  Android: `canAskAgain` does not matter, a refusal is `denied`; a response that says `granted: false` while its status says
  granted counts as `undetermined`.
- **The microphone notice is re-read when the app returns to the foreground** (`refreshMicrophoneOnForeground`, mounted by
  `RecordingNotices`). Swift read it on every 0.5 s tick, which is how a permission given in Settings made the notice go. The
  notice shows only while a recording runs, as in Swift.
- **The notice buttons** are the platform's: the "Dismiss" and "Open Settings" pills are `infoFill` with the accent label (the
  SwiftUI `.bordered` large style).

### JS-only guards (not in Swift; each has a test)

- A second start or stop while one runs is refused (`busy`), so a double tap cannot start two flights or persist one twice. A stop
  confirmed while the start is still running waits for it and then stops (it is not dropped).
- A stop that throws (the coordinator's promise can reject; Swift's cannot) is shown as a `recordingFailed` problem, and the
  store is not left busy.
- A `persist` that rejects is a `saveFailed` result with the same notice as Swift gives for it.
- The stop dialog closes by itself if the recording ends some other way (a stale dialog would stop nothing).
- A microphone answer still on its way when the recording state changes is dropped (it belongs to the earlier recording).
- A permission check that fails is shown as an audio problem (`audioSessionFailed`); the recording still starts.
- A plan that cannot be stored with the flight (`saveRouteLegs` rejects) is ignored, like Swift's `try?`; the recording and
  the flight are not affected.
- A Settings page that cannot be opened is ignored (Swift `openURL` does not report it either).

### Tests

Ported by name: `RecordingProblemSeverityTests` (2: the caution/warning split) and `MapGPSRecordingFixesTests`'
`discardedEmptyShowsNoticeSavedDoesNot` (`recordingNotices.test.ts`, 20 tests with the copy and press rules).
The rest of `MapGPSRecordingFixesTests` is other tickets': the `GPSFailureReason` cases (A1), Clear Direct-To (map) and the
debrief eligibility cases (U8b); `RecordingStopPathCharacterizationTests`' `TrackRecorder` suite is A1's. Swift has no other
test of the view model, so the store's 46 tests are written from the Swift source, over a real `RecordingCoordinator` with the
L4 fakes: following the coordinator, start, press, the stop dialog, stop and persistence, the problems, the microphone, Settings.
`microphonePermission` (port 4, adapter 9) and `refreshMicrophoneOnForeground` (4) complete the 83 tests of U8a.
Every guard was mutation-checked (a mutant that removes it fails a test).

### Fidelity capture (Q1)

Three scenes are registered in `ios-capture.sh`, `android-capture.sh` and the launch list in `app/index.tsx`, no floors:
`recording` (microphone off and the audio failing: both amber), `recordingstopped` (after a stop with no track: the failure in
red and the not-saved notice) and `recordingstop` (the confirmation). They run a real store over a coordinator on fakes with a
clock that stands still. The web preview adds buttons that drive the store (press the record button, no track on the next
stop, audio fails, microphone off or on); they are web only and do not appear in a native capture. As for U7, there is no
SwiftUI reference to compare against (the Swift debug hooks open only `map` and `log`).

## U8b: replay

The replay screen over the L8 `ReplayEngine`. Flight Detail, the debrief and the CVFR section (the rest of U8b) follow in the next
section.

### Ported

- `ViewModels/ReplayViewModel.swift` -> `src/ui/state/replayStore.ts`, a vanilla Zustand store that mirrors the engine's state
  (position, playing, speed, muted, marker, readouts, transcript line, phase fractions) and holds what the view model held:
  panel visibility, auto-follow, the speed picker, the loading state and the error. `loadFlight` resolves the audio, reads through
  the engine and opens the panel only when the flight has a transcript.
- `Views/Flights/ReplayView.swift` -> `src/ui/replay/ReplayScreen.tsx` (the four panes: a recording is running, loading, error with
  Retry, the replay) and `ReplayControls.tsx` (play and pause, the speed picker, re-centre, the GS / ALT / HDG readouts, the
  transcript toggle, the muted note, the line card over the map, with the scrub bar under them).
- `Views/Flights/TimelineScrubBar.swift` -> `TimelineScrubBar.tsx`; `TranscriptPanelView.swift` -> `TranscriptPanel.tsx`.
- `Views/Flights/ReplayMapView.swift` and the replay methods of `Services/MapService.swift` -> `ReplayMap.tsx`: a separate map with
  the track as an orange 3 pt line and the position as a 24 pt orange disc with a white outline and a 4 pt white dot, fitted to the
  track with 50 pt of padding once the style has loaded, following the marker until the pilot pans. `ReplayMap.web.tsx` draws the
  same track flat for the web preview (the native map has no web build, like `MapSurface.web.tsx`).
- The rules that are not drawing are in `src/domain/replay/replayView.ts` (title, times, spoken time, phase abbreviations, speeds,
  readouts, pane choice, the card over the map) and `replayMap.ts` (the track and marker as GeoJSON, the bounds).
- Shared pieces added to the app: `ui/components/BorderedButton.tsx` (`.bordered` and `.borderedProminent`; the recording notices
  use it too) and `NavBar` in `ui/form/Form.tsx` (the inline bar `FormScreen` already drew, for the screens that are not a form).

### Seams the app shell (I1) fills

- Make one `ReplayEngine` and one store per screen: `createReplayStore({ engine, source, openAudio })`. `source()` resolves to the
  `RecordingDatabase` (D4), which already satisfies `ReplaySource`, or to null when it cannot be opened (the screen then says
  "The recording database could not be opened. Reinstall Kanaf."). `openAudio(relativePath)` is the replay audio adapter (A3, #46):
  it resolves the path under the app's data directory and returns null when the file is not there.
- Mount `<ReplayScreen flight store recording onBack />` where the replay is shown; `recording` is the U8a recording store (the
  screen waits for a running recording to end). Flight Detail's "Replay Flight" button (the next section) opens it.
- The replay map uses `assets/base-style.json` with the sectional switched on, as the spike's `MapSurface` does. Once M1 (#44) is on
  main, take the style from its `surfaceModel` instead of the copy in `ReplayMap.tsx`.

### Swift quirks kept (owner approval needed to change)

- The replay fits the bounding box of the track (`fitMapToTrack`), so a track across the antimeridian zooms out to the world and the
  line is drawn the long way. Not handled: the app's regions (US, Israel) never cross it.

- The title with only one airport is "KPAO to " (the other side is empty), as Swift builds the string.
- The panel header says "1 segments": Swift has no singular.
- The flight is loaded when the screen appears with no recording running, and is not loaded again when a recording that was
  running at that moment ends: the screen stays at "Loading flight data...". (Opened from Flight Detail while idle this does not
  happen; a recording started after the load only hides the replay behind "End the recording first" and the replay is intact when it ends.)
- The replay keeps playing, audio included, behind the "End the recording first" note.
- The speed, and with it the muted note, survive a reload: that is the engine's (L8), not the screen's.

### Swift differences

- **The slider is a pan responder.** React Native has no slider in core. The track, thumb, ticks and times are as in Swift; screen
  readers adjust it by a tenth of the range (SwiftUI's step). The phase labels overlap when markers are close, as they do in Swift.
- **The speed picker is a card under the speed button** with a tap-away backdrop, not a system popover.
- **Translucent fills** stand in for `.ultraThinMaterial` and `.regularMaterial` (no blur view among the dependencies).
- **Any user gesture on the map turns auto-follow off.** Swift looked for `.gesturePan`; the MapLibre React Native event only says
  that the user moved the camera.
- **The marker is two circle layers**, not an image symbol: the icon is a circle, so the heading rotation was never visible. The
  heading stays a feature property.
- The controls over the map stop growing at xxxLarge text (`.dynamicTypeSize(...xxxLarge)`); the transcript timestamp stacks above
  its text from 1.6x font scale (SwiftUI's accessibility sizes).
- `spokenReplayTime` follows `DateComponentsFormatter` (full style, leading zero units dropped, "1 minute, 0 seconds"); it has not
  been compared with a device.

### JS-only guards (not in Swift; each has a test)

- A load that is no longer the latest (a newer load, or cleanup) does not change the state, does not reach the engine, and
  releases the audio player it opened. Swift reads synchronously.
- An audio file that exists but cannot be opened replays the track without audio.
- Only a failed read is a read error: what a listener of the store does with the loaded state is not reported as one.
- A time that is not a number reads as 0:00 (Swift `Int()` traps), a track of fewer than two points draws no line (a one-position
  GeoJSON line is invalid) and the bounds are a loop (a spread overflows the stack on a long track).

### Tests

Swift has no test of the replay view model or the replay views, so all 102 are written from the source. `replayView.test.ts` (60:
title, times, spoken time, abbreviations, speeds, readouts, pane choice, the card, capitalisation), `replayMap.test.ts` (11: the
GeoJSON, the bounds, a 300,000-point track) and `replayStore.test.ts` (31: over a real `ReplayEngine` with a manual tick scheduler
and a fake audio player: loading, failures, overlapping loads, playback, speed, the panel, cleanup). Every guard was
mutation-checked. The screens have no render tests (the repo has no test renderer set up on main yet; U3 adds one).

### Fidelity capture (Q1)

Two scenes in both capture scripts and the launch list, no floors: `replay` (paused at the turn at Afula, the transcript panel
open) and `replayfast` (4x with the audio muted, the panel closed so the line shows over the map, the map panned away so the
re-centre button shows). A pattern flight from Haifa (300 points, 25 minutes) on a real engine. The native scenes include the real
map, which loads its tiles from the network, so they wait for `WAIT` seconds like the other screens that are not the spike's map.
